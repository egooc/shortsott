**전부 죽은 게 아니라 특정 단계만 죽었다.** 이게 중요하다:

| 단계 | 결과 |
|---|---|
| `setup`(MCP 직접) | 한때 1101 → 05:0x 경 **복구됨** |
| `start` · `assets` · `env` · `probed` | 정상 |
| `rinbox_source` (ingest) | 정상 — 전사도 재사용(유료 0) |
| **`rinbox_plan`** | **1101 (4회) → 복구 뒤 정상** |
| `rinbox_camera` | 1101 (2회) — ★뒤에 밝혀진 바로는 **내 payload 탓이었다**(아래) |

죽은 두 단계는 **워커 안에서 편집 엔진이 실제로 도는 단계**다.
가벼운 단계는 다 산다. 그래서 «일시적 네트워크 장애»가 아니라
**그 코드 경로의 결함**으로 본다.

**아닌 것으로 확인된 원인:**
- 요청 본문 크기 — `rinbox_source` 가 같은 147KB payload 로 통과했다.
- payload 내용 — payload 없는 맨 `setup` 도 한때 1101 이었다.
- 실행기 구버전 — rinbox27ja 의 팩을 bootstrap 으로 최신(4174줄)으로 갈아 끼운 뒤에도
  `rinbox_camera` 가 똑같이 1101 이었다.

★**정정(05:2x):** `rinbox_camera` 의 1101 은 서버 장애가 **아니었다.**
한 샷에 카메라 점을 **세 개** 준 것(`[[t1,cx],[t2,cx],[t3,cx]]`)이 워커를 터뜨리고 있었다.
점을 하나로 줄이자 **그 자리에서 바로 렌더됐다.** 같은 모양을 rinbox28ja 에서는 전에 성공했으니
서버 쪽 회귀로 보이지만, 반려가 아니라 **500 으로 죽는다**는 점이 문제다.
→ **카메라 점은 샷당 하나만 줘라.** 피사체가 움직이면 컷을 쪼개는 편이 안전하다.
→ 그리고 **같은 1101 이라도 단계마다 원인이 다를 수 있다** — 「서버 장애」로 뭉뚱그리지 말고
   payload 를 단순화해 한 번은 갈라 보라.

**대응:** 두드리기를 멈췄다. 재전송은 득이 없고 접수 기록만 꼬인다.

### 이 과정에서 새로 확정한 엔진 규칙

**내레이션 그림은 `source` 에서 앞으로 자란다** — `picture = [source, source+길이]`.
뒤 컷 `source_in` 을 넘으면 거기 맞춰 당겨지고, 당긴 자리의 부분 샷이 15프레임 미만이면 또 앞으로 밀린다.
그래서 `source + 길이 < 뒤 컷 source_in` 이면 같은 샷 안에 틈이 남아 `same_shot_source_gap` 으로 반려된다.

★**반려되면 길이를 추측하지 마라.** `boundary_issues` 의 `from_frame` 이 엔진이 실제로 그림을 끝낸 프레임이다.
`실제 길이 = from_frame/30 − 내가 준 source`. 그걸로 새 source 를 계산하면 한 번에 통과한다.
컷을 `from_frame` 으로 옮겨도 통과하지만 앞 대사 꼬리가 딸려 들어온다 — **컷은 두고 source 를 늦춰라.**

### 또 하나 고친 것 — 철회 편이 웹 예약을 되살린다
