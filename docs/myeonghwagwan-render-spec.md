# 명화관 렌더 명세 — 자체 렌더러가 맞춰야 할 모양

소유주 지시 (2026-10-08)
> "편집표는 양쪽 공통이 아니라 **볼케이노 명화관이 맞고 그걸 기준으로 우리 스타일을 지켜야지**"
> "우리 ko랑 ja 스타일로 유지되게끔 하고 **볼케이노 서버 없이도 계속 되야지.** 업데이트는 반영하고"

기준은 볼케이노 명화관이 **실제로 낸 결과물**이다. 말이 아니라 숫자다.
뽑는 도구: `python scripts/render_contract.py <워크디렉토리>`
기준선: `server/data/render_contracts/myeonghwagwan-{ko,ja}.json`
(2026-10-08 `lsr01`(KO) · `lsr02-ja`(JA) 실측 — 둘 다 AGY 없이 완주한 판)

---

## 1. 화면·소리 — ko·ja 공통

```
해상도      1080 x 1920
프레임율    30/1  (CFR)
영상코덱    h264
소리        48000 Hz · 2ch · aac
라우드니스  -13.5 ~ -13.6 LUFS   (LRA 4.7~5.6)
자막 좌표계 PlayResX 1080 · PlayResY 1920 · WrapStyle 2 · ScaledBorderAndShadow yes
```

★`-13.5 LUFS` 는 두 편이 각각 -13.6/-13.5 로 나온 값이다. **목표값으로 삼되 ±0.5 는 같다고 본다.**

## 2. 자막 스타일 — 글꼴만 다르고 나머지는 똑같다

견줘 보니 ko·ja가 어긋나는 항목은 **글꼴 5줄이 전부**였다.

| 스타일 | 크기 | 색 | 외곽선 | 정렬 | ko 글꼴 | ja 글꼴 |
|---|---:|---|---:|---:|---|---|
| `Head` | 99 | `&H00FCFBFC` | 4 | 8 | Cafe24 Ohsquare | Noto Sans JP **Bold** |
| `Narr` | 82 | `&H00FCFCFC` | 5.5 | 5 | Cafe24 Ohsquare | Noto Sans JP **Medium** |
| `Dialogue` | 82 | `&H0019FFF7` | 5.5 | 5 | **SeoulHangang M** | Noto Sans JP **Medium** |
| `Effect` | 70 | `&H0002FEF6` | 4 | 5 | Cafe24 Ohsquare | Noto Sans JP **Medium** |
| `Credit` | 64 | `&H00999999` | 0 | 8 | Cafe24 Ohsquare | Noto Sans JP **Bold** |

여백은 다섯 스타일 모두 `MarginL 20 · MarginR 20 · MarginV 0`, `SecondaryColour &H000000FF`,
`OutlineColour`·`BackColour` 는 `&H00000000`, Bold/Italic 플래그는 전부 0 (ja 는 글꼴 이름으로 굵기를 낸다).

★**ko 의 `Dialogue` 만 다른 글꼴(SeoulHangang M)이다.** 해설(Narr)과 원음 대사(Dialogue)를
  글꼴로 구분하는 것이 ko 스타일이다. ja 는 굵기로만 구분한다. 이걸 통일하지 마라 — 우리 스타일이다.

## 3. 자막 배치

```
Head   \pos(540, 211) 과 \pos(540, 298)   — 제목 두 줄, 위쪽 정렬(8)
Narr   \pos(540, 1305)                    — 해설, 가운데 정렬(5)
Dialogue 같은 아래쪽 띠
```
`Head` 둘째 줄은 색이 다르다 — 첫 줄 `&H00FCFBFC`(흰색), 둘째 줄 `&H001BFFF6`(노랑).
즉 **제목 둘째 줄이 강조색**이다. 인라인 `{\c&H...&}` 로 준다.

## 4. 편집표(입력) 모양

`edit.json` — 볼케이노가 정한 형식이고 **우리가 바꾸지 않는다.**

```
title       ["윗줄", "아랫줄"]            2줄
credit      "작품명"                      화면 크레딧
editorial   { version, premise, title_promise,
              beats: [{role, what, evidence, sequence_indices}] }
              role 순서: setup → escalation → reversal → payoff
narration[] { id, text, cards[], source }  source = 해설 밑에 깔 그림의 소스 시각
sequence[]  { narration: "nN" }  |  { source_in, source_out, captions[] }
```

실측 분포(2편): 해설 3개 · 원음컷 3~4개 · 큐 80~100개 · 길이 124~172초.

## 5. 쓰는 법

```bash
# 기준선 뽑기 / 갱신
python scripts/render_contract.py D:/volcano-runs/<wd> --save myeonghwagwan-ko

# 자체 렌더러 결과를 기준선과 견주기
python scripts/render_contract.py <우리_렌더_폴더> --against myeonghwagwan-ko

# 두 결과를 직접 견주기 (ko↔ja, 또는 볼케이노↔자체)
python scripts/render_contract.py <A> --compare <B>
```

견줄 때 **스타일·화면 규격만** 본다. 길이·프레임 수·라우드니스 LRA 는 편집표가 다르면
당연히 달라지므로 따로 «참고»로만 찍는다.

## 6. 업데이트를 어떻게 따라가나

1. `scripts/volcano_runner_watch.py` 가 07:00·19:00 에 실행기 변화를 잡는다(사례 166).
2. 렌더에 직접 영향 주는 파일이 바뀌면(`film_*` · `shorts_framing` · `subject_*`) **크게 알린다.**
3. 그 뒤 첫 볼케이노 회차의 결과로 `render_contract.py --against` 를 돌린다.
   - 계약서가 **안 바뀌면** 우리 렌더러는 그대로 둔다.
   - 바뀌면 바뀐 항목만 우리 렌더러에 옮긴다.

★**볼케이노 내부 코드를 부르지 않는다.** `film_editor.py` 를 직접 import 하면 그쪽 갱신에
  우리가 깨진다(린박스 세션 판단, 동의). 형식과 결과만 맞추고 코드는 우리 것으로 둔다.

## 7. 아직 계약서에 안 들어간 것

정직하게 적어 둔다 — 이 명세만으로는 아직 똑같이 못 만든다.

- **컷 경계의 실제 프레임 정렬** — 편집표의 `source_in/out` 과 결과물 프레임의 대응을 아직 안 쟀다.
- **해설 그림 구간의 화면 처리** — 확대/정지/패닝 여부. AGY 를 안 쓰는 판에서 무엇이 되는지 더 봐야 한다.
- **`flash_aliases`** — 1~2프레임짜리 원본 장면 처리. 2026-10-08 서버가 새로 넣었다(사례 166).
  23.976fps 소스에서 나오는 경우라 자체 렌더러도 처리해야 한다.
- **BGM·효과음** — 이번 두 편에는 `Effect` 큐가 0개였다. 쓰는 편으로 한 번 더 재야 한다.

## 8. 화면 치수 — **엔진 자산에서 가져온 값** (2026-10-09 정정)

★처음엔 완성본 화소를 재서 그림 창을 `y 516~1501` 로 적었다. **틀렸다.**
  편집 폴더에 엔진이 쓰는 **`chrome.png` 원본이 그대로 들어 있었고**(1080x1920 RGBA,
  ko·ja 동일 311,404B), 그 투명 영역이 진짜 창이다. 화소 측정이 작게 나온 것은
  창 가장자리의 부드러운 알파 때문이다. **자산이 있으면 자산이 정답이다.**

```

틀        assets/myeonghwagwan_chrome.png  (엔진 원본 그대로)
          위 = 붉은 커튼 · 아래 = 객석 · 가운데 투명

  그 10편은 전부 **캡컷 출력 폴더의 발행본**이었고, 발행본은 우리 캡컷 파이프라인

  교훈: «완성본»이라 할 때 **어느 완성본인지** 먼저 확인하라.
  볼케이노 명화관의 기준은 `D:/volcano-runs/<wd>/edits/<id>/final-*.mp4` 다.
  볼케이노 회차 8편 실측(lsr01·lsr02-ja·cg01-ja·cg02·wf01·wf01-ja…) 전부 흰색/노랑이었다.

### 정렬 — 스타일마다 다르다 ★
```

Narr    5 (가운데)       Dialogue 5      Effect 5
여백    다섯 스타일 모두 L20 R20 V0

5 로 통일하면 **제목이 반 줄만큼 아래로 내려간다**(실측 확인). 2항 표에 적어 두고도

**카페24 아네모네**다. 우리는 **파일의 실제 이름**을 쓴다 — 그래야 libass 가 찾는다.

## 10. 엔진 코드에서 가져온 규칙 (2026-10-09)

소유주 지시
> "린박스 랜더러 지금 더 만들고있어서 그거 어느정도 만들어지고 참조를 하되
>  **볼케이노의 명화관 작업 방식을 최대한 가져오는게 더 중요한거잖아**"

맞는 지적이었다. 린박스 뼈대를 기준으로 삼았더니 **거기서 베껴 온 값 여섯이 틀렸다.**
린박스 렌더러는 아직 만들어지는 중이라 기준이 될 수 없다. 기준은
`D:/volcano-runs/*/runner/film_editor.py` 와 볼케이노 완성본이다.

### 1. 해설 그림은 편집표가 정한 자리에서 시작한다
```python
# film_editor.py 662 · 728
a = narration[clip["narration"]]["source"] if "narration" in clip else clip["source_in"]
narration[n["id"]] = {"kind": "N", "source_in": n["source"], ...}
```
린박스는 «앞 컷 끝에서 이어서» 잡는다. **명화관은 `narration[].source` 를 쓴다.**
편집표가 정해 준 자리를 무시하고 있었다.

### 2. 음량은 2패스다
```python
# film_editor.py 1815~1820
norm = f"loudnorm=I={lufs}:TP={tp}:LRA={lra}"
... print_format=json 으로 재고 ...
norm += ":linear=true:" + "measured_I=…:measured_TP=…:measured_LRA=…:measured_thresh=…:offset=…"
```
1패스로 하면 -13.8 이 나왔다(목표 -13.5). 2패스로 바꾸니 **-13.6 — 볼케이노와 같다.**
무음일 때는 측정을 지어내지 않는다(엔진 주석: "Digital silence has no finite loudness").

### 3. 검은 띠를 먼저 걷어낸다
```python
# film_editor.py 786~804  measure_content()
컷 8개를 1초씩 cropdetect=24:2:0 → 최빈값
원본 절반보다 작은 표본은 버린다 → 없으면 통짜 프레임
```
그리고 cx 를 **그 알맹이 안에서** 센다(`content['x']`, `content['width']`).
통짜 프레임에서 세면 레터박스 원본에서 검은 띠째로 창에 들어가고 피사체도 밀린다.

→ `scripts/ass_diff.py` 로 렌더 전에 견준다. 3분짜리 렌더를 돌리고 화면을 봐야
  알던 것을 1초에 잡는다.

## 11. 장면별 확대 창 — **AGY 영수증 자리를 우리가 채운다** (2026-10-09)

소유주 지시: "이제 agy 영수값 대신해서 저걸 만들어야지 — view_width·crop 샷별 확대 창,
flash_aliases. 이걸 클로드가 잡아줘야지 프레임전사보면서."

### 엔진에 있는 두 길

| 칸 | 뜻 | 엔진 자리 | 어디서 왔나 |
|---|---|---|---|
| `crop: [가로비, 세로비]` | 장면마다 창 크기 + 가로·세로 가운데 | film_editor.py 1454~1477 | AGY 피사체 영수증 |
| `view_width: 가로비` | 가로만. 세로는 알맹이 전체, 남는 데는 검은 띠 | film_editor.py 1478~1494 | 사람이 손으로 정한 화각 |
| `same_as` / `side` | 한두 프레임 장면은 이웃 창을 그 시각에 | shorts_framing.py 88~100 | 서버 flash_aliases |

셋 다 `scripts/myeonghwagwan_render.py` 에 들어갔다(`pic_clip_shots` · `focus_pieces`).
엔진처럼 **한 ffmpeg 안에서** split → 장면별 trim·crop → concat 하고 `settb`·`setpts=N` 으로
시각을 출력 격자에 다시 매긴다. 조각을 따로 구워 붙이면 1프레임 조각 길이가 0 으로 쳐져
프레임을 흘린다(엔진 `joined_pieces` 주석의 사고 그대로).

### 영수증은 못 만든다 — 판독만 갈아 끼운다

`shorts_framing.resolve` 73줄이 영수증 **파일 해시**를 검사한다. 우리가 지어낼 수 없다.
그래서 바꾼 것은 **누가 피사체를 읽느냐** 하나다. 기하(배율·창 위치·보간)는 엔진 규칙을
읽고 다시 구현했다 — 엔진 코드는 가져오지 않는다.

    135~190퍼센트 확대 · 창은 지킬 영역을 품고 · 가운데는 ±0.5초 중앙값 · 둘레 여유 2.5퍼센트
    배율은 장면 id 의 sha256 에서 뽑는다(기계·재실행에 안 흔들린다)
    ★장면 id 를 엔진과 같은 '%.3f' % 시작초 로 쓴다 — 같은 상한이면 **같은 배율**이 나온다

### 누가 읽나 — 기계가 먼저, 내가 집는다

| 단계 | 누가 | 무엇 |
|---|---|---|
| `detect` | 린박스 `rinbox_faces`(YuNet, 초당 10프레임) | 얼굴 → 화자 고르기 → 머리+윗몸 네모 |
| `sheets` | ffmpeg + 격자 | 얼굴 없는 장면(화면·손·물건·항공샷)만 프레임판으로 |
| (손) | 클로드 | 프레임판을 보고 백분율로 네모를 적는다 |
| `solve` | 기하 | 배율·창·점 → `focus.json` |
| `review` | 그림 | 고른 피사체(초록)와 실제 창(빨강)을 장면마다 그린다 |
| (손) | 클로드 | 틀린 장면만 `override` 에 적는다 |

**lsr01 실측**: 장면 75개 중 기계 56 · 손 19 · 덮어쓴 것 1개(19.833).

### 여기서 배운 것

1. **표본이 성기면 오간 움직임을 놓친다.** 1.2초 간격으로 읽었더니 186.633 장면에서
   얼굴이 왼쪽으로 갔다 돌아오는 사이 창이 흐린 앞사람에게 갔다(출력 149초).
   볼케이노 완성본은 그 시각에 얼굴이 또렷했다. → 0.3초 간격 기계 판독으로 바꿔 고쳤다.
2. **흐린 앞사람이 또렷한 주인공을 이긴다.** 네 장면(11.900·51.667·59.367·103.900)에서
   어깨너머 앞사람에게 창이 갔다. 선명도(얼굴 **안쪽 60퍼센트** 라플라시안 분산 ÷ 대비)로
   거르면 다 고쳐진다. 네모 전체로 재면 머리카락·창문 경계 때문에 흐린 얼굴도 높게 나온다
   (린박스 세션이 83ko 에서 실측해 알려 줬다 — `rinbox_faces.sharpness`).
   ★린박스는 «흐리고 **또 큰**» 얼굴만 뺀다. 명화관 11.900 에서는 흐린 방해물이 주인공보다
     **작아서** 그 그물을 빠져나갔다. 그래서 우리는 크기 조건 없이 선명도만으로 거른다.
3. **얼굴 네모를 사람 크기로 부풀리면 안 된다.** 세로를 얼굴 높이의 3.5배로 주니
   거의 모든 장면에서 네모가 창에 꽉 차 확대가 1.0 으로 눌렸다(75장면 중 58장면).
   머리+윗몸은 얼굴 높이의 약 2.6배·폭의 2.2배다. 그리고 여유는 **창 안에 들어갈 만큼만**
   준다 — 클로즈업에서 반드시 보여야 할 것은 얼굴이지 어깨가 아니다.
4. **묶음은 프레임마다 검사해야 한다.** 가운데값만 보면 두 사람이 벌어지는 장면에서
   어느 순간 창을 넘는다(139.367). 넘으면 그 장면은 한 사람만 따라간다.
5. **AGY 와 남는 차이 하나**: AGY 는 프레임마다 보고 우리는 0.3초마다 본다.
   그 사이는 렌더 식이 선형으로 잇는다(엔진도 같은 식). 지금 실측으로는 어긋난 데가 없다.

### 장면 경계 — 흑백 필름에서는 **색 분포가 안 먹힌다** (2026-10-09 실측)

우리 장면 경계는 `read_cuts` 가 정한다 — **볼케이노가 이미 잰 값이 있으면 그것이 정답**
(`edits/*/source-shots.json` · `measurements.json`), 없으면 ffmpeg `select='gt(scene,0.35)'`.

린박스 세션이 흑백 사극(月影兵庫 1965)에서 자기 검출(`rinbox_screen.shot_cuts`,
HSV 12x6x6 히스토그램 거리)이 컷을 거의 못 잡는다고 알려 왔다. 그쪽 그림 창
(`rinbox84ja/_render/pic.mp4`, 1336프레임 · 평균 채도 **3.3/255**)으로 셋을 맞대 봤다.

| 재는 법 | 잡은 곳 |
|---|---|
| 린박스 `shot_cuts` (HSV 히스토그램) | **2곳** — 720 · 1222 |
| 회색 64칸 히스토그램으로 바꿔 봄 | **3곳** — 내 짐작은 틀렸다 |
| 회색 평균 절대차 > 40 (린박스 제안) | **8곳** — 121 306 439 593 720 846 1060 1222 |
| ffmpeg `gt(scene,0.35)` (우리 길) | **8곳** — 같은 자리, 하나도 안 틀렸다 |

**왜**: 흑백 필름은 샷이 바뀌어도 화면 전체의 **밝기 분포가 거의 그대로**다. 히스토그램은
화소가 어디 있는지를 버리므로 그 차이를 못 본다. ffmpeg 의 scene 점수와 평균 절대차는 둘 다
**자리를 보는(공간) 측정**이라 잡는다. 히스토그램 칸을 늘려도 소용없다 — 재는 축이 틀린 것이다.

컬러 소재(`rinbox83ko`, 채도 98.3)에서 문턱 40 은 21곳 중 3곳만 넘는다. 즉 **덧붙이는 검출로는
안전하다**(거짓 검출 0). 다만 컷 하나가 1221·1222 처럼 두 번 세어지면 없는 1프레임 조각이
생겨 경계 검사가 멀쩡한 렌더를 반려한다 — 2프레임 안의 검출은 하나로 합쳐야 한다.

★린박스가 `shot_cuts` 를 고쳐도 **우리 샷 나눔은 안 바뀐다**. `shot_focus` 는 `rinbox_faces` 의
`read_range` · `mouth_patch` · `sharpness` · 상수만 import 하고 `plan_range`(= `shot_cuts` 를
쓰는 쪽)는 안 부른다. 우리는 이미 끊어 놓은 샷 안에서만 얼굴을 읽는다.

### 린박스에서 받아 둘 것 — 재사용 관문 (2026-10-09, 아직 안 붙였다)

린박스가 `scripts/rinbox_reuse.py` 를 만들었다. 이번 편 컷의 **원음 대사 글자**를 12자 조각으로
썰어 다른 회차 폴더 전사에서 찾고, 그 자리가 그 폴더 편집표의 쓴 구간 안이면 재사용으로 본다.
소스 영상 ID 가 안 남은 옛 편까지 잡힌다.

명화관에 **쓸 만하다** — 한 영화에서 여러 편을 뽑을 때 같은 장면을 두 번 쓰는 걸 막는다.
장면 겹침으로 보기 때문에 «같은 영화 · 다른 장면»은 통과한다(ko/ja 가 같은 영화를 다른 장면으로
다루는 것도 막지 않는다 — 영화 단위로 막는 관문을 따로 만들면 안 된다).

지금은 안 붙인다. 명화관은 회차가 둘(lsr01 ko · lsr02-ja)이고 **원본이 서로 다른 영화**라
겹칠 게 없다. 검증할 거짓말 하나 없는 관문을 붙이면 «통과»가 늘 떠서 없는 안심을 준다.
같은 영화로 두 번째 편을 뽑는 날 붙인다. 그때 바꿀 것은 셋뿐이다:

1. `RUNS.glob('rinbox*')` — 접두사가 박혀 있다. `lsr*` 로(또는 인자로) 바꾼다.
2. `STATES` — 린박스 발행 기록이다. 명화관 발행은 `server/data/web_publish_state.json` ·
   `blotato_publish_state.json` 에 있다(`rinbox_publish_state.json` 에 lsr 은 0건).
3. ★`published_files()` 는 **파일 이름만** 맞대 본다. 린박스 출력은 `final-<해시>.mp4` 라 안전하지만
   **명화관 출력은 `final.mp4`** 다 — 그대로 쓰면 `final.mp4` 가 있는 폴더가 전부 «발행»으로 읽혀
   겹치는 것마다 ✗ 가 된다. 폴더 이름이나 전체 경로로 맞대야 한다.

### 린박스 `MARGIN` 2.5% 는 **우리 것과 다른 뜻**이다

린박스가 로고 여유를 2.5% 로 잡으며 «명화관 MARGIN 과 같은 값»이라고 알려 왔다. 숫자는 같지만
재는 대상이 다르다 — 우리 `MARGIN` 은 **피사체 네모 둘레**의 여유(배율 상한과 clamp 계산에 쓴다),
린박스 것은 **창 가장자리에서 로고까지**의 여유다. 한쪽을 조율해도 다른 쪽이 따라갈 이유가 없다.
나중에 «같은 값이니 상수 하나로 합치자»고 하지 말 것.

### 세로축 — 헷갈리기 쉬운 자리

정사각형 창에서 **배율 1.0 인 클로즈업은 세로 자유도가 0** 이다(창 높이 = 알맹이 높이).
그래서 그런 장면은 세로 이동이 정확히 0 으로 나온다 — 배선이 틀린 게 아니라 clamp 가 묶는 것이다.
확대가 되는 장면에서는 움직인다(48.100 창의 0.112 · 103.900 창의 0.104).
